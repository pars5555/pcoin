PCoin

Accept PCN payments

Everything needed to take PCoin in your own product: deposit addresses derived from an xpub you keep offline, one HTTP API to watch them, and the rules that stop you crediting money that is not there.

Two production integrations already follow this guide — AiControl and checker.pc.am. Every rule below exists because it was got wrong once, usually expensively. Where a rule looks paranoid, the reason is stated.

1. The model

PCN top-up is one-way and custody-free. Your server derives a deposit address per user, watches it, and credits when the payment is deep enough. It never holds a private key, so it is cryptographically incapable of moving funds. That is the design, not a limitation.

  1. Generate a BIP39 seed offline.
  2. Derive the account xpub at m/84'/9444'/0'.
  3. Put only the xpub on the server.
  4. Derive one address per user from it — non-hardened children, so the xpub alone suffices.
  5. Poll the explorer. Credit when the gates in §4 pass.

Coin type 9444' is load-bearing. PCoin kept Bitcoin's xprv/xpub version bytes, so the same seed under coin type 0' derives live Bitcoin keys. Get this wrong and you are generating real Bitcoin addresses you cannot spend from.

2. Deposit addresses

Addresses are BIP84 native SegWit, hrp pc, so they look like pc1q…. Derive m/84'/9444'/0'/0/index, one index per user, allocated MAX(index)+1.

Index order is signup order. Anyone holding your xpub can derive every address, query them all, and read your entire customer payment history in order. Treat the xpub as confidential — and note it cannot be rotated without orphaning every address you have already issued.

Never put a child private key on the server either: an account xpub plus one child privkey lets an attacker derive every sibling private key.

3. The explorer API

https://explorer.pc.am/api — HTTP, no auth, no key, no rate limit worth worrying about at this size.

EndpointUse
GET /api/statustip height, index health
GET /api/address/{addr}confirmed / unconfirmed / lifetime balances
GET /api/address/{addr}/txstransactions — see the shape trap below
GET /api/tx/{txid}authoritative height and is_coinbase
POST /api/addressesbatch: which of these have activity

Do not use node RPC

Two concrete reasons, both of which have cost real time:

  • There is no address index in the node. The only way to ask "what did this address receive" is scantxoutset, which is O(entire UTXO set) and globally serialised behind a process-wide flag. One HTTP request could stall every other RPC on that node.
  • Wallet RPCs are -rpcwallet scoped. getaddressinfo, gettransaction and getbalances will answer confidently about the wrong wallet if two are loaded.

Response shapes

  • Transactions live under confirmed.items[], not at the top level.
  • The address summary has no is_coinbase — its keys stop at net_pcn. Fetch /api/tx/{txid} for that.

4. The gates

All of them. None optional.

GateValueWhy
confirmations20 recommended, 5 minimum~69 chain tips seen; ~3% lifetime stale rate
deposit height≥ 2800below it difficulty is frozen

index healthblocks_unwound == 0reorg in flight = untrustworthy counts

Gate on the deposit's height, not the tip

Below height 2800 the difficulty is frozen at 1e0b7c33 — the legacy retarget fires only every 2016 blocks and does not run again until 4032. Anyone renting hashrate can rewrite that stretch of history cheaply and the chain cannot push back. A tip-based gate credits a pre-LWMA deposit the instant the tip crosses 2800, which is exactly wrong.

// wrong: credits old, cheap-to-reorg coins once the tip moves
if (tipHeight >= MIN_HEIGHT) credit();

// right: judge the deposit's own block, and assert it twice --
// once from the address summary, once from the authoritative /tx
if (deposit.height < MIN_HEIGHT) reject("pre-LWMA");

Coinbase deposits need 100 confirmations

startmining "<address>" needs no wallet, so a user can point a miner straight at their deposit address. Without a maturity check each 50 PCN reward would credit ~95 blocks before it is spendable at all.

5. Failure resolves nothing

A call that failed, timed out, or answered "I do not know" resolves NOTHING. It can never advance a record, never clear one, and never authorise a credit.

optInt("confirmations", 0) on a call that may not have happened is a bug: an unanswerable question silently becomes a definite "not confirmed". Model unknown as its own state. Every failure path must hold, never credit.

Validate addresses locally. Do not rely on the API to reject bad input — an integration that trusts a remote service to validate is one outage away from crediting nonsense. Check the bech32 checksum yourself, and reject a Bitcoin bc1… address on its hrp.

6. Idempotency

Key the ledger on the outpoint — txid plus vout — with a unique index, and treat a duplicate-key error as already applied rather than an error. A retrying poller must be a no-op.

Do not put UNIQUE(ref_type, ref_id) on a shared credit ledger: a debit and a refund both legitimately write ('card', <same id>). Use a separate nullable idempotency column.

If your credits are integers, carry the sub-credit remainder forward per address. Flooring each deposit silently eats up to a whole credit every time.

7. Reorgs: detect, never auto-reverse

Store block_hash at credit time and re-check it for deposits credited in the last ~7 days. If the funding transaction is no longer in that block, flag and alert — do not claw back automatically. A reversal is itself exploitable, and on this chain it will eventually hit an honest user. A human posts the compensating entry.

  • Never judge a reorg on an unreachable or reorg-in-flight index — skip instead.
  • Never flag on a truncated history: if the fetch hit its row limit, an absent transaction may simply be older than the window.

8. Amounts

Amounts arrive as bare JSON numbers. There is no string form — JSON_BIGINT_AS_STRING only affects integers. Convert to satoshis with integer arithmetic and round once, deliberately. Never accumulate in floats.

9. Before you go live

  • Seed generated offline; paper backup verified by restoring it — a backup is not a backup until it has been loaded
  • Only the xpub on the server
  • Deposit-height gate on the deposit's own height, asserted twice
  • Coinbase deposits require 100 confirmations
  • Every failure path holds rather than credits
  • Ledger idempotent on the outpoint
  • block_hash re-checked for recent credits; flags, does not reverse
  • Addresses validated locally
  • Tested against the live chain, not only fixtures
