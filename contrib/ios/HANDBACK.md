## 1. The derivation unit test, passing against PCOIN.md §6.4

Written before any UI, as the brief asks. `PCoinKit` is a Swift package
specifically so this runs on any machine with Swift — no simulator, no signing,
no device:

```
cd contrib/ios/PCoinKit && swift test
```

The §6.4 vectors are asserted in full: seed, master xprv, master fingerprint,
account xprv **and** xpub, both descriptors **with their published checksums**,
the three receive addresses and the three change addresses.

```

Test Case '-[PCoinKitTests.PublishedVectorsTests testCoinTypeSeparatesPcoinFromBitcoin]' passed
Test Case '-[PCoinKitTests.PublishedVectorsTests testWordlistIsTheCanonicalOne]' passed
Executed 67 tests, with 0 failures (0 unexpected) in 20.797 seconds
```

The other 64 exist because agreeing with the other two PCoin wallets is not the
same as being right. They pin this implementation to published vectors from
outside the project:

| test file | what it pins |
|---|---|
| `PublishedVectorsTests` | PCOIN.md §6.4, and that coin type 9444' really does diverge from Bitcoin's tree |
| `StandardVectorsTests` | BIP32 vectors 1 and 3 (3 is the leading-zero case), the BIP39 Trezor vectors including the "TREZOR" passphrase, RIPEMD-160's own vectors including the million-`a` case, bech32/bech32m |
| `SigningTests` | **BIP143's native-P2WPKH vector — sighash, DER signature bytes and final serialisation.** A signature match also proves RFC6979 determinism; a random nonce would fail it |
| `WatchOnlyTests` | CKDpub and CKDpriv derive the same 50 addresses, and hardened public derivation is impossible |
| `AmountsTests` | no floating point drift, comma refused rather than guessed, exponent grammar matching the JVM |
| `AddressAndSpendTests` | address rejections say *which* kind, fee never underpays, dust change goes to the fee, every signature verifies |
| `PaymentUriTests` | the three §3 behaviours, plus the whole Android case list |
| `RedactAndIndexTests` | no secret can reach a log; lifetime counters do not gate; `network.has_it` decodes null as nil |

Two vectors I could not verify from memory were **recomputed with an independent
implementation** (Python `hashlib`) before being written down, and the first of
the set matches the digest published in BIP39 itself — so those are two
implementations agreeing, not this code agreeing with itself. One
"vector" I first transcribed for bech32 turned out to be wrong; it was replaced
with values generated by that same independent implementation rather than left
in.

### How the URI reaches the app under test, stated precisely

The test hands the URI to `handle(_:)` — **the same function `onOpenURL` calls**
— via a DEBUG-only launch argument. So `PaymentRequest` parsing, the refusal
rules and `SignRequestView` are exercised exactly as for a real link.

What that does **not** exercise is iOS's own scheme dispatch. That half was
proven separately and by hand, with the command the brief names:

```
xcrun simctl openurl booted "pcoin:pc1qnfk7xenwzxx7h4mx88g004crlx0m2zcjg3nq4j?amount=7.25"
```

which made the system offer **"Open in 'PCoin Wallet'?"** — the registration
working. Driving that dialog from inside XCUITest has to go through Safari, and
Safari's address bar is unreliable about keyboard focus under test; that is a
property of Safari, not of this app, and not worth a flaky suite.

### The two test hooks, and why they are safe

Both are compiled out of release builds with `#if DEBUG`:

* `-uiTestResetWallet` — forgets the wallet. It **cannot create one and cannot
  spend**; a launch argument that installed a key would be a back door into the
  only thing this app protects. The test taps the real setup buttons instead.
* `-uiTestOpenURL <uri>` — delivers a payment URI through the ordinary URL
  entry point. It carries no key and authorises nothing; the screen it opens is
  the one that is deliberately incapable of spending.

### A real bug the UI test found

**A brand-new wallet's twelve words were generated and never shown.**

`RootView` switched on `store.hasWallet`, and `createWallet()` sets that flag the
instant the key is stored — which is *before* the phrase is displayed. So the
setup screen was swapped for the home screen the moment the key existed, and the
one screen a new wallet cannot skip was skipped. A user would have ended up with
a funded-capable wallet and no recovery phrase, with only the home screen's
"Write down your recovery phrase" card to save them.

It was invisible until a UI test printed **what was actually on screen** instead
of only reporting that the expected thing was missing — the screen dump showed
the home screen, complete with a freshly derived receive address. Fixed by
making the setup flow own its own exit (`SetupView.onFinished`); `RootView` now
decides once on appear and only ever switches *back* to setup, never away from
it.

Two smaller ones, both mine, both worth recording because they are the same
shape — a guard that could not fire:

* The generated Xcode project never set `SWIFT_ACTIVE_COMPILATION_CONDITIONS =
  DEBUG`, which Xcode's own templates do. So `#if DEBUG` was **false in the
  Debug build**, and the correctly-guarded test hook was compiled out of the
  very build meant to have it.
* The simulator Keychain fallback listed `errSecAuthFailed` and `-25293` — the
  same number twice — so it covered two codes and missed whatever the simulator
  actually returns. It now falls back on **any** non-success status.

## 3. Where "identical to Android" had to bend

Seven places. The full argument for each is in `README.md`; this is the list.

| # | difference | why |
|---|---|---|
| 1 | **No node in the app.** Balances, history and UTXOs come over HTTP; the chain line names explorer.pc.am rather than a peer count | iOS forbids exec and JIT |
| 2 | **iOS signs, using libsecp256k1** vendored from this repo's own `src/secp256k1` | The Android Kotlin curve says of itself it "must never be reused for signing"; Android's node does the signing and there is no node here |
| 3 | **The unlock is one screen earlier** — at "Check this send", not "Send now" | The review screen promises real figures from the built transaction, and building means signing, which means the key |
| 4 | **A send has three outcomes, not two** — sent / rejected / **not confirmed yet** | `POST /api/tx` answers about the *network*, and `network.has_it` is three-valued |
| 5 | **Spending needs 1 confirmation** | Core spends its own 0-conf change; a light client cannot tell its own change from a replaceable incoming payment, and this chain reorgs routinely |
| 6 | **An account xpub is cached ungated** so reading a balance never prompts | Nobody expects Face ID to look at their own balance. The xpub can watch everything and spend nothing; the privacy cost is stated in `WatchOnlyStore` |
| 7 | **Gap-limit scan (20, floor 40) instead of a 1000-address import** | Android's node rescans locally for free; every address costs a request here |
| 8 | **A Simulator with no passcode stores the phrase UNGATED**, says so in Settings and raises a warning | `.userPresence` cannot be satisfied without a passcode, and a simulator has none. Contained by `#if targetEnvironment(simulator)`, so it cannot exist in any device build |

Also different, and smaller:

* **The Settings warnings are a different list.** Android's three — battery
  optimisation, "Pause app activity if unused", blocked notifications — all
  exist because a node runs in the background there. None of those conditions
  exists on iOS, so reproducing them would be inventing problems. The iOS list
  is: no device passcode, phrase not written down, key not in the Secure
  Enclave, explorer index not current. Every check fails open, exactly as
  Android's do.
* **Wording changed in five places only**, each marked `IOS:` in `Strings.swift`
  with the reason — the chain line, the "nothing to fix" line, the screen-lock
  sentence, "Google Play" → "the App Store", and the no-wallet sentence, which
  no longer says "Open PCoin Wallet" because the app is already open.

**Universal links are prepared but not active.** `https://pc.am/pay` needs an
`apple-app-site-association` file naming a real Team ID, and that URL is a 404
today (measured 2026-09-10). The entitlement and an AASA template are in the
repo with the three steps to switch them on. The `pcoin:` scheme is registered
and carries every payment request meanwhile, which is what the hop page at
`site/pay/index.html` already falls back to.

## 4. The broadcast blocker

**Not worked around, and no longer blocking.**

When this started, the blocker was real. I re-measured it before writing any
code rather than taking the brief's word for it:

```
POST https://explorer.pc.am/api/tx  {"hex":"00"}
-> {"error":{"code":"broadcast_unavailable", ...
     "this API refuses to relay through a node that can spend."}}
```

explorer2 answered identically. I raised it, did **not** design around it, and
did **not** reach for `--allow-wallet-node`. The send path was written straight
through to `POST /api/tx` on the assumption it would be fixed server-side.

It was fixed mid-build, and `PROMPT-IOS-BROADCAST-READY.md` appeared. The client
was then reworked to the real response shape, and verified live:

```
POST https://explorer.pc.am/api/tx  (a structurally valid transaction
                                     spending an outpoint that does not exist)
-> {"txid":"a756c4b4ebd7f349...","accepted_by_node":false,
    "error":{"code":"rejected","message":"bad-txns-inputs-missingorspent",...},
    "network":{"has_it":false,"state":"rejected","peers":3},
    "tx":{"vsize":110,"input_count":1,"output_count":1}}
```

That round trip is worth more than a green tick: the relay **parsed a
transaction this code serialised** and reported its vsize, input count and
output count correctly, which is an independent check of the serialiser against
a real PCoin node.

`network.has_it` is carried through to the screen as three states and never
flattened. `?? false` on it would tell somebody their payment failed while it is
confirming — and a transport failure is reported as *unknown* too, because the
txid is fixed by the submitted bytes before the node is contacted, so a lost
response has lost nothing.
